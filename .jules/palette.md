## 2024-07-16 — Accessible Custom Controls with Tailwind `peer`

**Found:** Custom radio buttons (Service Type, Timeline) and checkboxes (Add-ons) in `CalculatorSection.tsx` were built using visual `div` and `button` elements, while the native `input` elements were either completely hidden (`className="hidden"`) or missing, making them inaccessible to keyboard navigation and screen readers. Similarly, `LoginPage.tsx` fields were missing proper `useId` hook generated ID linkage between labels and inputs.
**Why it existed:** Developers often hide native form controls to apply custom styling without realizing that `display: none` removes the element from the accessibility tree and prevents keyboard focus.
**Fix:** Refactored custom controls to use the `<label>` wrapper pattern. Replaced `className="hidden"` with Tailwind's `sr-only peer` on the native `<input type="radio">` and `<input type="checkbox">` elements, ensuring they remain accessible. Moved the native input *before* the visual `div` and applied `peer-focus-visible:ring-2` to the visual `div` to properly render focus rings when the hidden native input receives keyboard focus. Used React's `useId()` for form fields.
**Learning:** Always use `sr-only` combined with the `peer` class instead of `hidden` when building custom form controls in Tailwind to maintain full accessibility and keyboard focus indicators. Ensure native inputs are direct preceding siblings of their visual replacements.
**Watch for:** Other custom UI components (like toggles, switches, custom selects) across the application that might be using `hidden` instead of `sr-only peer` for their underlying native controls.
