## 2025-07-02 — Custom Input Accessibility Patterns
**Found:** Custom interactive elements (checkboxes, radio buttons) were breaking keyboard accessibility and screen reader support. Checkboxes used `className="hidden"`, which completely removes them from the accessibility tree and prevents focus. Radio buttons were implemented as generic buttons without roles or states.
**Why it existed:** Tailwind's utility-first approach often encourages hiding native inputs to build custom visual representations, but `hidden` (`display: none`) is destructive for accessibility.
**Fix:** Replaced `hidden` with `className="sr-only peer"` on checkboxes, allowing the native input to maintain focus while remaining visually hidden, and styled the adjacent custom element using `peer-focus-visible`. For custom radios, grouped buttons with `role="radiogroup"` and applied `role="radio"` with `aria-checked` and `focus-visible` to the buttons.
**Learning:** Never use `hidden` on native form inputs when building custom UI. Always rely on `.sr-only` coupled with the `.peer` pseudo-class pattern in Tailwind to link focus state to the visual stand-in. All generic elements mimicking native controls must explicitly declare their ARIA role and state.
**Watch for:** Other areas in the app where custom toggle switches, checkboxes, or segment controls are built using hidden inputs or generic buttons.
