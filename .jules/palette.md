## YYYY-MM-DD — Form Labelling & Aria Accessibility Overhaul
**Found:** Custom `<Input>` and `<Select>` components lacked `id` attributes and appropriate `htmlFor` mapping on labels, impeding screen readers. Icon-only buttons lacked contextual `aria-label`s, and loading states on buttons didn't communicate to assistive tech (via `aria-busy`).
**Why it existed:** The rapid development of internal dashboard forms likely prioritized visual fidelity over underlying a11y DOM attributes. Developers were passing data bindings and labels, but not considering the underlying HTML tree structure.
**Fix:** Extended `<Input>` and `<Select>` components to require an `id` prop, mapped this `id` explicitly to `<label htmlFor={id}>` and `<input id={id}>`. Propagated unique IDs to all calling sites. Inserted `aria-label="Toggle password visibility"` in the Login form. Passed `aria-busy={loading}` for button components engaged in asynchronous data operations.
**Learning:** Custom wrapper components frequently lack proper accessible labeling unless explicitly enforced by design system constraints. Always ensure a unique `id` is linked to `<label htmlFor={id}>`. Icon-only buttons must include an `aria-label`. Buttons triggering async operations must track state with `aria-busy={loading}`.
**Watch for:** Other forms or custom inputs (e.g., custom checkboxes or radio buttons) throughout the app that might be mimicking input functionality without native HTML input properties linked by `id`s. Check other usages of `lucide-react` icons inside raw `<button>` elements.
