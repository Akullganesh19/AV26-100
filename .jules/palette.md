## 2024-05-18 — Systemic Form Input & Custom Control Accessibility Gaps
**Found:** Several components missed critical accessibility bindings: custom form input wrapper components (`Input`, `Select`) didn't automatically generate IDs or link their labels to inputs via `htmlFor`, resulting in screen readers being unable to identify form fields. Furthermore, custom interactive controls like checkboxes used `display: none` (`hidden` in Tailwind) on their native inputs, and custom radio controls built out of `<button>` elements lacked proper `role="radio"` and `aria-checked` states.
**Why it existed:** The `Input` and `Select` components were built as fast, reusable wrappers but the developers likely overlooked that standard HTML `label` linking requires unique IDs, which aren't guaranteed if multiple instances of the same form are rendered. For the custom controls, visual styling was prioritized over semantic state, leading to visually hiding the native inputs which broke keyboard focus and screen reader capability.
**Fix:** Updated `DiagnosticsCenter.tsx` to use `React.useId()` inside generic wrapper components to automatically associate `<label htmlFor={id}>` with `<input id={id}>`. In `CalculatorSection.tsx`, replaced `hidden` with `sr-only peer` for custom checkboxes to preserve keyboard focusability and styled custom radio buttons with appropriate `role="radiogroup"`, `role="radio"`, and `aria-checked` attributes. Also fixed basic ARIA labeling in `LoginPage.tsx`.
**Learning:** Always use `React.useId()` when building generic input wrappers to guarantee unique DOM IDs and accessible form labeling. Custom input controls must never use `display: none` on the native control; always use `sr-only` to preserve keyboard interactions.
**Watch for:** Other custom form wrappers or toggle controls built without `<input type="checkbox/radio">` that might rely entirely on `onClick` state without communicating that state to screen readers.
