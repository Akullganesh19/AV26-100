## 2026-06-24 — Accessible Custom Form Controls in Calculator

**Found:** Custom visual radio buttons and checkboxes in `CalculatorSection.tsx` were built using interactive `div`s and `button`s or completely visually hidden `className="hidden"` native inputs. This broke keyboard navigation (no focus visibility) and screen reader support (no form association).
**Why it existed:** The developer prioritized matching the high-fidelity visual design (custom red active circles, specialized layout) over native semantic form controls. Native inputs were hidden improperly using `display: none` (`hidden`), which removes them from the accessibility tree and keyboard tab order.
**Fix:** Wrapped the custom UI groups in `role="radiogroup"` / `role="group"` with `aria-labelledby`. Swapped `hidden` for Tailwind's `sr-only peer` on the native `<input>` elements, and added `peer-focus-visible:ring-2` to the custom visual indicators so keyboard focus state matches the visual design constraints without compromising native functionality.
**Learning:** You can perfectly preserve custom design constraints while remaining 100% accessible by combining `<label>`, `<input className="sr-only peer" />`, and visually adjacent `div` elements styled with `peer-checked:` and `peer-focus-visible:`. Never use `hidden` to hide a native input you want users to interact with.
**Watch for:** Other custom toggles, switches, or stylized form elements throughout the codebase (e.g., in `DiagnosticsCenter.tsx` or `SimulationLab.tsx`) that might be using `className="hidden"` on native inputs or missing proper ARIA grouping.
