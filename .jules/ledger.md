## 2025-02-14 — Atomic Update for Simulation State Day Advance
**Value type:** Current day counter / quota tracking within mission simulations
**Drift risk found:** The `SimulationService.advance_day` function exhibited a severe read-modify-write race condition (`sim.current_day += 1`) unprotected by locks or atomic database updates. Concurrent clicks on "Advance Day" (or rapid retry scenarios) would all read the same `current_day` value and simultaneously increment it to the identical next day, subsequently double-triggering high-risk events (like `CLINICAL_SURGE` or `FORECAST_SPIKE`) for that specific day without properly progressing the simulation counter.
**Fix:** Refactored the in-memory increment to an atomic PostgreSQL update operation: `update(SimulationState).values(current_day=SimulationState.current_day + 1).returning(SimulationState.current_day)`. The subsequent event processing logic was updated to use the atomically `new_day` returned, ensuring strict idempotency and exactly-once execution for any given scenario day.
**Proven by:** Simulated 3 simultaneous asynchronous requests attempting to advance the day. Confirmed via assertions that the final `current_day` strictly reaches 3 and returns [1, 2, 3] distinctly, preventing any duplicate processing of day 1.
**Other balances to check:** Any other counter logic that relies on `.count` and simple memory increments (`+= 1`) inside the `backend/app/services` directory (such as pipeline runs).
