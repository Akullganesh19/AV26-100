## 2024-05-18 — Active PII Exposure in Application Logs
**Data traced:** PII (email, password, clerk_id, ssn)
**Exposure found:** System `logger` instances routinely logged dictionary kwargs using the `extra={}` block without structlog redaction. Certain logs directly logged unredacted email identifiers as strings inside error messages (e.g., `logger.error(f"Failed to send email to {email}")`).
**Fix:** Upgraded global logging formatters. `setup_logging` now uses standard python `logging` routed through `structlog.stdlib.ProcessorFormatter` with a custom `redact_pii_processor` recursive dictionary and list walker with a fallback standalone email regex mask. This strictly and safely redacts `SENSITIVE_KEYS` locally and strips standalone emails globally from log lines before stringification.
**Coverage confirmed:** The fix was empirically confirmed to correctly format `logging.info/logging.error` methods, mask isolated string emails while preserving context, and mask PII deep inside nested dictionary and list values provided via `extra={}` kwargs. Verified by Python scratch script integration test (and deleted). Tests did not fail.
**Still exposed elsewhere:** While logging is sanitized structurally, unredacted query string parameters might still be captured by upstream application load balancers, and raw PII values are still stored in plain-text inside `User` instances (e.g. `clerk_id`) and potentially other database schemas with no structural deletion or TTL path established yet.
