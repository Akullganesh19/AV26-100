## 2025-07-14 — Defuse Mass Assignment and Exception Swallowing
**Found:** (1) The `register` endpoint inherited `UserCreate` (from `UserBase`), allowing users to self-assign their `role` (e.g., to "admin") or `is_active` flag. (2) The Redis token revocation check in `get_current_user` used a broad `except Exception:` block that swallowed both `redis.RedisError` (failing open on infrastructure failure) and explicitly raised `HTTPException`s (silently bypassing token revocation).
**Why it existed:** (1) Convenience inheritance of Pydantic models for user creation without explicitly separating client-provided fields from internal fields. (2) Rushed attempt to ignore JWT verification errors without catching specific exception types.
**Fix:** (1) Explicitly instantiated the `User` object with safe defaults (`role=UserRole.OFFICER`, `is_active=True`) in the route handler, ignoring those fields from `user_in`. (2) Refactored exception handling to explicitly catch and re-raise `HTTPException`, fail closed on `redis.RedisError`, and swallow only `jose.exceptions.JWTError`.
**Learning:** Always explicitly catch specific exceptions (especially `HTTPException` in FastAPI dependencies) to prevent failing open, and never trust inherited Pydantic schemas for sensitive fields without explicit server-side overrides.
**Watch for:** Other endpoints directly spreading Pydantic inputs into SQLAlchemy models, and other broad `except Exception:` blocks in authentication/authorization middleware.
