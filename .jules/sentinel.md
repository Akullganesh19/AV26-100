## 2024-05-24 — Token Revocation Bypass in Auth Dependency
**Attacked:** JWT token revocation check in `backend/app/api/deps.py` (`get_current_user`).
**Found:** The logic to enforce token revocation explicitly raised a 401 `HTTPException` if the token's JTI was found in Redis. However, a subsequent broad `except Exception:` block caught this `HTTPException` (because it inherits from Python's base `Exception`), silently swallowed the error, and allowed execution to fall through to standard signature verification. Since the token was otherwise valid, a revoked token would be successfully authenticated. Furthermore, if Redis was unavailable, the exception was also swallowed, causing it to "fail open."
**Severity:** 🔴
**Fixed or flagged:** Fixed. Updated the try/except block to explicitly catch and re-raise `HTTPException` so the 401 response reaches the client. Also added explicit handling for `redis.RedisError` to raise a 500 `HTTPException`, ensuring the system fails securely (closed) when the revocation infrastructure is down. Added regression tests to `backend/tests/api/test_deps.py` and `test_deps_redis_error.py`.
**Systemic pattern:** Broad `except Exception:` blocks surrounding security validations or infrastructure calls can silently swallow intended failure paths (like `HTTPException`) and infrastructure errors, turning what should be a secure failure into a vulnerability. Look for `except Exception:` blocks in other dependencies or decorators.
