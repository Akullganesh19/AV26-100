## 2024-08-09 — Token Revocation Bypass & Mass Assignment
**Found:** 1) `jwt.JWTError` and `redis.RedisError` were swallowed by a broad `except Exception:` block during auth dependency execution. 2) The `/register` endpoint was mapping the `role` field from request body to the new user. 3) 500 error responses exposed `str(e)`.
**Why it existed:** 1) Hasty error handling during Redis implementation for token blacklisting. 2) Convenience during prototyping for `UserCreate` schema. 3) Ease of debugging during development phase.
**Fix:** 1) Updated `except` blocks in `backend/app/api/deps.py` to catch specific exceptions and explicitly raise HTTPExceptions when appropriate. 2) Hardcoded `UserRole.OFFICER` in `backend/app/api/routes/auth.py`. 3) Used Python's `logging` module to log `exc_info=True` and returned generic "Internal server error" messages from routes.
**Learning:** 1) Broad `except` blocks are incredibly dangerous in authentication/authorization paths; they mask failures and can default to 'fail open' behavior. 2) Pydantic schemas shared between client/server can inadvertently expose mutable fields if not explicitly dropped or overridden on the backend.
**Watch for:** 1) New dependencies being added with similar catch-all exception handling. 2) Other object creation flows where user input is mapped directly to database models (e.g., updating user profiles).
